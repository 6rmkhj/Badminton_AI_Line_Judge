# 잔여 오탐 보완 검증 — 0.5.4

**기존 평가에서 두 사례가 개선됐지만, 남은 오탐을 모두 해결하지 못했다.** 고정된 참조 기준을 충족한 기존 영상은 **5/13 → 7/13**이며 이전 성공 5개는 유지됐다. 코드와 설정을 동결한 뒤 새로 평가한 8개 영상에서는 위치를 평가할 수 있는 4개 모두 실패했다(**0/4**). 현재 버전의 일반화 성능은 입증되지 않았다.

이 수치는 원본에서 AI가 표시한 대략적인 최초 낙하 주변의 시각·위치와 선택 후보의 일치 여부다. 독립적인 사람의 정답 검수, 코르크 접촉점 정확도 또는 IN/OUT 정확도가 아니다. 모든 평가 결과는 `REVIEW`이며 `contact_observed=false`를 유지한다.

## 채택한 변경

- **관측 경로의 연속성:** 실제 하강 정점을 건너뛰고 작은 밝은 조각을 따라가는 후보를 구별한다. 경쟁 후보가 실제 접근·이후 관측을 공유하고 크기와 경로가 맞는 경우 더 충실한 경로를 우선한다. 좌표를 옮기거나 없는 관측을 생성하지 않는다.
- **원본 장면을 이용한 후보 순위:** 실제 원본 7프레임에서 화면 아래와 연결된 색상 영역과 후보의 거리를 확인한다. 기존 후보 순위에 0.5–1 범위의 제한된 가중치만 적용한다. 바닥의 의미를 인식하거나 접촉을 증명하는 기능은 아니며, 불확실한 장면 근거는 중립으로 처리한다. 명시적인 검토 영역·접촉 근거의 우선순위는 보존한다.
- **관측 근거 검증:** 명시적인 보간점과 좌표·프레임이 일치하는 강한 정지 배경 근거를 실제 이동 관측과 구분한다. 오래되거나 불일치하는 근거를 현재 관측의 증거로 재사용하지 않는다. 자동 원본 검사 래퍼는 실험에서 개선이 없어 포함하지 않았다.
- **원본 디코딩 보장:** 장면 순위 기능이 켜져 있으면 검출기의 원본 탐색 설정과 무관하게 실제 원본 픽셀을 읽는다.

기본 검출기 자체는 0.5.3과 동일하다. 새로운 원본 복구 검출기, 실험 추적기와 TrackNet 가중치는 배포하지 않는다.

## 검증 결과와 범위

| 평가 자료 | 실행 범위 | 결과 |
|---|---|---|
| 기존 24개 | 동일한 검출·코트 보정 결과와 실제 원본 픽셀로 변경된 추적·이벤트 단계를 재실행 | 위치 평가 가능 13개 중 5 → 7개 일치; 11개는 가림·대상 불확실성으로 점수 제외 |
| 개선된 2개 | 동결한 코드로 검출부터 근거 영상 생성까지 전체 새 실행 | ordinary-4-a, ordinary-12-a 모두 단계 평가와 동일한 선택 |
| 최초 A1/B1 | 동결한 코드로 전체 새 실행 | 기존 기준 유지; A 5.18px, B 1.70px |
| 추가 8개 | 코드·설정 동결 및 참조 봉인 후 전체 새 실행 | 평가 가능 4개 중 0개 일치; 나머지 4개는 가림으로 점수 제외 |

기존 24개 전체를 새로 검출한 결과로 표현하면 안 된다. 검출기·보정 코드와 설정이 같음을 확인한 후 그 결과를 재사용했다. 위의 전체 새 실행은 추가 8개, 최초 A/B 2개, 개선 사례 2개인 총 12회다. 개선 사례는 기존 24개에 포함되므로 서로 다른 원본은 총 34개다. 0.5.3의 추가 8개 전체 실행은 하지 않았으므로 새 영상의 전후 개선률은 제시하지 않는다.

추가 영상은 같은 프로젝트에서 이번 보완 회차에 보류한 자료다. 프로젝트 역사 전체에서 처음 본 영상이나 외부 체육관의 독립 검증이라고 주장하지 않는다. 참조 좌표, 시간 구간, 허용오차와 평가 제외 기준은 예측 후 변경하지 않았다. A/B 이름만으로 동일 사건·시각 정합을 가정하지 않고 각 시점을 별도로 평가했다.

### 확인한 두 개선

| 영상 | 이전 선택 | 0.5.4 선택 | 원본 대조 |
|---|---|---|---|
| ordinary-12-a | 150프레임, 참조 오차 6.61px | 151프레임, 4.25px; 허용오차 6px | 실제 흰 깃털의 하강·반전 관측을 선택. 관측 물체 중심이며 코르크 접촉 확정은 아님 |
| ordinary-4-a | 42프레임, 옆 코트의 높은 라켓 반전 | 188프레임, 2.37px; 허용오차 8px | 주 대상 셔틀의 하강과 반동 사이 위치. 누락 구간의 **추정 중심**이며 188프레임의 실측 접촉점은 아님 |

기존 7개 일치는 관측 물체 중심 4개와 추정 중심 3개로 구분한다. 위의 2개를 제외한 기존 22개 선택은 바뀌지 않았다. 전후 비교와 원본 근거는 [연속성 검사](remediation/continuity-source-review.json), [장면 순위 검사](remediation/scene-source-review.json), [최종 평가](remediation/final-evaluation.json)에 보존한다.

### 남은 실패 원인

기존 평가 가능 영상 중 `8k-2-b`, `ordinary-4-b`, `ordinary-18-a`, `uhdhd-4-a`, `uhdhd-4-b`, `uhdhd-5-a`는 여전히 실패한다. 실제 낙하 주변 관측이 없거나, 희미한 셔틀의 조각들이 서로 다른 궤적으로 나뉘거나, 대상 셔틀 대신 다른 움직임·잔상으로 이어진다. 일부 프레임에 가까운 검출점이 있다는 사실만으로 같은 셔틀의 낙하를 복구했다고 판정하지 않았다.

추가 영상에서 확인한 실패는 다음과 같다. 원본과 선택 궤적의 대조 이미지와 기록은 [추가 8개 원본 검토](remediation/final-new8-source-review.json)에 포함했다.

| 영상 | 실제 실패 |
|---|---|
| 8k-3-a | 대상 셔틀 대신 선수 옷 가장자리를 선택 |
| ordinary-1-a | 실제 셔틀을 따라갔지만 최초 낙하 대신 두 번째 바운드를 선택 |
| uhd4k-1-b | 높은 타격 이후 벽·보 주변의 다른 요소로 연결 |
| uhdhd-1-a | 셔틀에서 신발로 추적 대상이 바뀜 |

`ordinary-1-a`에는 첫 낙하 주변의 추정 후보가 이미 3순위에 있다. 그 이후 반동과 두 번째 바운드 접근이 정확히 같은 실측점들을 공유하는 것도 확인했다. 하지만 최초 후보 앞에 13프레임의 관측 공백이 있고 바닥 접촉·라켓 부재를 입증하지 못한다. 단순히 앞선 반전을 우선하면 낮은 라켓 타격을 낙하로 선택할 수 있다. 두 번째 후보만 낮추면 관련 없는 원거리 후보가 올라오는 문제도 있어 이 규칙은 채택하지 않았다.

## 실험했지만 제외한 변경

- 원본 해상도 잔여 후보 복구는 희미한 흰 깃털의 일부 실측점을 찾아냈지만, 전체 궤적과 최초 낙하 선택으로 이어지지 않았다. 제한된 추가 후보 예산과 연결 단계에서 필요한 연속 관측이 탈락하는 문제도 확인했다. 일부 점의 검출 성공을 낙하 정확도 개선으로 계산하지 않았다.
- 실측점 연결 추적기 역시 필요한 관측이 빠지거나 서로 다른 조각으로 검출된 구간을 회복하지 못했다. 특정 영상에 맞춰 관측 누락·반동 기준을 낮추지 않았다.
- 원본 픽셀 검사 래퍼는 해당 중간 비교에서 6/13 → 6/13으로 개선이 없고 처리 비용을 늘려 제외했다. 이는 최종 7/13과 별개의 구성 비교다.
- 고정 TrackNet 모델을 이미 공개된 실패 2개에 적용한 개발 실험에서 기본 방식, 모델 결합, 모델 단독 모두 **0/2**였다. 한 사례는 실제 두 번째 바운드에서 원거리의 잘못된 대상으로 오히려 바뀌었다. CPU 모델 추론만 합계 약 432초가 추가됐다. [고정 모델 실험 기록](remediation/rejected-fixed-model/README.md)을 남기고 제품에 포함하지 않았다.

추가 8개의 정답을 확인한 이후 수행한 위의 모델·순서 진단은 개발 실험이다. 동결 버전의 0/4 결과와 섞거나 새로운 독립 평가로 취급하지 않는다.

## 실행·화면 검증과 배포

- 코드 `7306efe267e40f4f8539c0439711ec54c2afcd41`, 버전 `0.5.4`를 추가 8개 결과 공개 전에 동결했다. 이후 문서·증거만 추가했다.
- 전체 Python 테스트 **684개 통과**, 53.10초, 종료 코드 0. [로그와 소스 해시](software-verification/verification.json)를 기록했다. 이 통과 수는 영상 정확도가 아니다.
- 실제 전체 분석으로 생성한 최초 A/B와 개선 2개 결과를 데스크톱 및 375/390px 모바일 화면에서 확인했다. 원본·재생 영상의 프레임 시각, 탐색, 재생, 새로고침과 미디어 바이트를 대조했고 JavaScript 예외와 앱·미디어 요청 실패는 없었다. 브라우저 업로드부터 새 분석을 시작하는 흐름의 검증은 아니며, [브라우저 기록](software-verification/release-0.5.4-browser/README.md)에 범위를 적었다.
- 최초 A1은 첨부 용량 제한 때문에 저장소의 같은 이름 파일로 검증했으며 첨부와의 바이트 동일성은 확인하지 못했다. B1은 첨부 파일과 SHA256이 일치한다. [원본 회귀 기록](remediation/control-regression.json)을 확인할 수 있다.
- Windows 휴대용 패키지의 파일 해시와 ZIP 무결성을 검사한다. Linux 환경에서 Windows 실행 파일을 직접 실행한 검증은 수행하지 않았다.

[0.5.4 Windows 패키지](https://github.com/6rmkhj/Badminton_AI_Line_Judge/archive/refs/heads/downloads/windows-portable-0.5.4.zip)는 압축을 푼 뒤 `START.bat`로 실행한다. 자동 판정에는 사용하지 말고 `REVIEW` 근거와 추정 여부를 확인해야 한다.

원시 수치와 원본·참조·코드·설정 해시는 [최종 평가 JSON](remediation/final-evaluation.json), [평가 규칙](remediation/protocol.json), [근거 목록](remediation/final-inventory.json), [배포 검증 기록](remediation/release-validation.json)에 보존한다. [0.5.3 평가](GENERALIZATION_VALIDATION.md)는 이전 기준선으로 유지한다.
